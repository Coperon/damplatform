## Locked product (do not re-infer from prototype SQL)

- A **tenant** is a hard isolation boundary and **owns** its library.
- Cross-tenant file visibility is **public share links only** (not folder grants between tenants).
- A client **user belongs to exactly one tenant**. Two client companies ⇒ two accounts.
- **Operators** are not tenant members. They have **full break-glass** on every library, always with an explicit acting tenant for library operations.
- A **file belongs to exactly one collection**. Editors and tenant admins may **move** a file within the tenant.
- **Everyone in a tenant sees the whole library.** Roles control actions, not folder visibility.
- Collection **parent is immutable** after create. Tree is a **forest** of top-level folders. No unassigned files. Upload always targets a collection.
- **Delete collection** destroys the subtree (folders + files + object storage).
- **Delete tenant** is operator-only and **refused** while users, resources, or collections exist.
- Roles: `operator` | `tenant_admin` | `editor` | `viewer`.
- Share links: **tenant admin and operator only**. Collection share = **direct files only**. Creator chooses `view` or `download`.
- Viewers **may download originals in-app**.
- Audit: **security and admin events**, not every preview.

## Invariants (enforce, do not comment)

1. A resource owned by tenant A is never returned to a tenant-B user except via a valid unrevoked unexpired share token whose scope includes that resource.
2. Every collection and resource has `tenant_id NOT NULL`.
3. A resource’s `collection_id` references a collection with the same `tenant_id` (composite FK).
4. Collection hierarchies are acyclic. Parent cannot be updated; insert cannot set `parent_id = id`.
5. Operators have `tenant_id IS NULL`; every other user has `tenant_id NOT NULL`.
6. Every tenant-scoped query in the DAL is parameterized with the acting tenant (operator included). There is no unscoped “list all files” except operator tenant-directory APIs.
7. Authorization is never “hide the button.” UI may hide; server always checks.
8. Storage keys are server-issued. Client-supplied keys are rejected.
9. Folder delete removes DB rows then object bytes; never the reverse.
10. Tenant delete fails if any user, resource, or collection remains.

Enforcement layers: database constraints (2–5, 10) + DAL (1, 6, 8) + authorization module (7) + tests (all) + transactions for delete/move (9).

## Classification

### REQUIRED before production

- New ownership schema; drop grant table, M2M junction, role matrix, magic role ids.
- Fail-closed authorization and tenant-scoped DAL.
- Load user row (status, role, tenant) on every request; do not trust JWT capability flags.
- Login refuses inactive users.
- Bind upload keys to a server-issued pending upload.
- Gate share `original`/`download` on access level.
- Unique hashes for share and invite tokens.
- Characterization tests, then explicit data mapping, then cutover.
- Tenant isolation + authorization matrix tests.
- Destructive folder delete also deletes storage objects.
- Tenant delete RESTRICT until empty.
- Security/admin audit events.
- Env/secret validation at boot.
- Database backups/PITR (operations, not code).

### SHOULD before production

- Sentry (or equivalent) + structured request logs.
- Playwright for login, upload, share, cross-tenant deny.
- CI `next build` in addition to typecheck/tests.
- Expired pending-upload cleanup (cron or script).
- Health check that probes DB (already) and storage.
- Remove unused Redis from Compose.
- RLS as defense in depth **after** DAL is the only query path.

### CAN wait

- Resumable uploads.
- Content-addressed deduplication.
- Full library activity history.
- Thumbnail job queue.
- Custom metadata-template product work beyond per-tenant fields.
- Product analytics/metrics beyond errors and audit.

### NOT worth changing

- Splitting into NestJS / microservices / Kubernetes.
- Redis or BullMQ for rate limits or thumbnails (until in-request work is proven insufficient).
- Keeping `tenant_collection_access` or recursive access CTEs as the isolation model.
- Two schema sources of truth.

## Global constraints (copied into every plan)

- Single Next.js 16 full-stack app. No NestJS, no Redis, no job queue in this program.
- Drizzle schema is the only table/column/constraint source of truth.
- Raw SQL only for `tsvector` / `pg_trgm` / triggers / subtree SQL / one-time cutover.
- `bcryptjs` for passwords, not `bcrypt`. `jsonwebtoken` HS256, not `jose`.
- Parameterized queries only. 401 = unauthenticated, 403 = authenticated but forbidden.
- Fail closed on authorization. Empty required fields → 400. Unique violations → 409.
- All config from environment. Migrations append-only; never edit an applied file.
- App stays runnable after each phase.
